## Goal

Prove that a real user action travels through the complete production path and
produces one truthful, visible, internally consistent result across the staged
draft, authenticated API request, repair compiler, immutable child plan,
`PlanDiff`, independent evaluation certificate, route geography, itinerary,
Compare, Evidence, and MapLibre renderer.

This phase is not complete when schemas validate, an endpoint returns HTTP 200,
or an eligible child exists only in backend memory. It is complete only when a
production-like browser renders the exact independently evaluated child returned
by the backend and exposes a map acknowledgement whose plan identity, geometry
hash, and marker IDs agree with the preview response.

operations. The serialized backend child plan is the sole preview source of
truth.

## Interaction Semantics

### Stage

- Validate and append the typed operation to `WorkspaceStore`.
- Show `Draft staged. Run Preview repair to generate and evaluate a child itinerary.`
- Keep the accepted itinerary plan ID, route, and active markers unchanged.
- Draft-only overlays may appear only when visibly labeled as draft evidence.
- Do not claim the repair ran.

### Preview repair

- Submit the entire current valid draft with expected revision.
- Run the real compiler/repair/evaluator/geography pipeline.
- Keep the parent active for failed, unsupported, ineligible, or
  non-renderable results.
- Render an eligible child only after the response passes strict normalization
  and every visible surface resolves the same child identity.
- Show `Preview ready` only after a matching map acknowledgement arrives.

### Accept

- Accept only the currently rendered eligible child.
- Bind the confirmation request to the child plan ID/hash, proposal revision,
  diff, certificate, and last map acknowledgement.
- Persist through the existing immutable repository, decision ledger, and
  accepted-plan pointer transaction.
- Preserve the prior parent and survive refresh.

### `draft-preview-v2`

New previews use a coordinated strict schema version because the existing
`draft-preview-v1` frontend normalizer rejects unknown keys. Persisted v1
proposals may be restored for historical evidence, but they are invalidated as
active rendered previews and require a new Preview action.

The existing `{"proposal": ..., "session": ...}` envelope remains. The v2
proposal preserves current lineage/evidence fields and adds:

```typescript
type DraftPreviewV2 = {
  schema_version: "draft-preview-v2";
  request_id: string; // exact-equal compiled_request.source_request_id
  preview_status: "eligible" | "ineligible" | "unsupported" | "failed";
  comparison_eligibility: "eligible" | "ineligible" | "not_evaluated";
  map_renderability:
    | "ready"
    | "missing_geometry"
    | "invalid_route"
    | "not_applicable";

  parent_plan_id: string;
  parent_plan_content_hash: string;
  child_plan_id: string | null;
  child_plan_content_hash: string | null;
  child_plan: CanonicalPlanRecord | null;

  diff_identity: DiffIdentity;
  plan_diff: PlanDiffRecord | null;
  certificate_identity: CertificateIdentity;
  evaluation_summary: EvaluationSummary | null;
  geography_plan: GeographyPlanV2 | null;
  geography_content_hash: string | null;
  blocking_findings: Finding[];
  warnings: Finding[];
};
```

The server computes `geography_content_hash` using the repository's canonical
JSON/content-hash convention over the exact serialized geography payload. The
browser recomputes and validates it before rendering.

Rules:

- `eligible` requires a non-null child, diff, evaluation, geography, and all
  exact identity bindings.
- `map_renderability="ready"` requires eligible evaluation, complete road-valid
  geography, no strict fallback, and matching plan identity.
- `ineligible`, `unsupported`, and `failed` cannot be map-renderable.
- Findings use closed codes and sanitized user-facing messages.
- No `NaN`, infinity, missing-as-zero, or arbitrary extra keys.

## Storage and State

- `WorkspaceStore` remains the persistent owner of selections, drafts,
  proposal, permissions, and revision.
- `PlanRepository`, decision ledger, and accepted-plan pointer remain the
  persistent owner of accepted decisions.
- `PreviewRuntime` and `MapRenderAcknowledgement` are browser-runtime state.
  They are initialized from a validated proposal, cleared on draft mutation,
  stale response, failed render, session switch, logout/session expiry, or
  disposal, and never persisted as acceptance truth.
- A v1 persisted proposal may be displayed as historical Evidence but cannot
  enter `PREVIEW_RENDERED` without a v2 rerun and acknowledgement.
- Parent and child artifacts remain immutable.

## UI, API, and Internal Integration

1. `previewDraft()` creates a monotonically increasing epoch and captures
   session ID, expected revision, draft hash, and accepted parent ID/hash.
2. It sets `PREVIEW_RUNNING`, clears any old map acknowledgement, and sends the
   existing authenticated POST request.
3. The API calls `ProductService.preview()` and returns `draft-preview-v2`.
4. The browser verifies the envelope, schema, source request, draft, parent,
   child, diff, evaluation, route, and geography hashes.
5. Before committing the response, it verifies that the epoch, session,
   revision, and draft are still current. A stale response is discarded without
   rendering or toast success.
6. An ineligible or non-renderable response enters an explicit blocked state and
   preserves the parent render.
7. An eligible/renderable response enters `PREVIEW_DATA_READY`; all panels read
   the same `activeRenderContext()`.
8. The map controller renders and emits a matching acknowledgement.
9. Only then does the app enter `PREVIEW_RENDERED` and show Preview ready.
10. Accept requires the same response and acknowledgement identities; refresh
    loads the durable accepted child through the existing W5 pointer path.

## Validation and Failure Rules

- The live path is disabled unless the explicit billed-mode flag, approved exact
  prompt hash, synthetic run ID, `gpt-5.4-mini`, low effort, and attempt cap all
  match the authorization record.
- The browser-visible message, product API message, prompt bundle user message,
  persisted conversation turn, and transport witness must be byte/equality
  bound; no test-only replacement response is permitted.
- The provider interpretation must strict-parse, pass local semantic validation,
  and produce exactly one actionable `replace_nearby` intent for the expected
  registered target/candidate before `Add to draft` can be enabled.
- Unsupported semantic intent never becomes a different operation.
- Invalid draft input fails before revision/draft mutation.
- Preview requests require authentication and exact expected revision.
- Old responses cannot overwrite newer state.
- Missing or mismatched child, diff, certificate, route, or geography identity
  fails closed.
- An ineligible child never becomes the active render context.
- `map_renderability="ready"` requires strict road-valid complete geography.
- Map ready without matching acknowledgement is not preview ready.
- A map acknowledgement from an old render generation is discarded.
- Accept fails if acknowledgement, proposal, session revision, or accepted
  parent changed.
- Parent artifacts remain byte/hash immutable in every scenario.
- Failures retain drafts for correction and provide stable user-facing reason
  codes without raw paths or secrets.

## Error Handling and Recovery

- **Provider unavailable/auth/rate/quota/timeout failure:** show the existing
  sanitized Copilot error, persist no proposal or draft, preserve the parent
  render, record the bounded diagnostic/attempt count, and stop without an
  automatic semantic resubmission. Only the adapter's one transient retry may
  consume the second authorized attempt.
- **Provider clarification/refusal/invalid structured output:** render the
  truthful conversation state, disable `Add to draft`, keep revision/draft/map
  unchanged, and fail the E2E-1L happy-path assertion.
- **Browser closed or stale revision during provider wait:** the late response
  may be stored only under the authenticated conversation rules; it must not
  stage, preview, or render against a different session revision.
- **API/repair failure:** enter `PREVIEW_FAILED`, retain draft, preserve parent,
  and allow retry.
- **Independent ineligibility:** enter `PREVIEW_INELIGIBLE`, show exact blocking
  findings, retain draft, and do not render child geography.
- **Missing/invalid geography:** report `missing_geometry` or `invalid_route`,
  preserve parent, and never show Preview ready.
- **Map render failure:** clear acknowledgement, retain validated response as
  evidence-only data, preserve parent as active, and expose text route evidence.
- **Stale response:** discard silently from active state and log a bounded
  diagnostic code; never overwrite the newer request.
- **Refresh before acceptance:** restore the proposal only as data-ready; require
  a fresh map acknowledgement before Preview ready or Accept.
- **Refresh after acceptance:** load the accepted pointer/repository child and
  render it as accepted, not preview.
- **Rollback:** use the existing append-only W5 transaction; never mutate a
  historical parent or child.

- child/diff/evaluation/geography identity equality;
- ineligible/non-renderable combinations rejected;
- forged child, geometry, marker, route, or acknowledgement rejected; and

FastAPI endpoint
  -> security/revision validation
  -> WorkspaceStore
  -> FrozenDraftCompiler / repair service

  -> PlanEvaluator
  -> geography builder
  -> strict response serializer

External route/provider data may use pinned deterministic evidence. Internal
repair, evaluator, diff, geography, persistence, and serializer boundaries must
not be mocked.

### Browser tests

- launch `scripts/run_product_app.py` on a free loopback port with disposable
  state and deterministic Copilot;
- click actual controls and call the actual local API;
- wait for the exact response and map acknowledgement, not a timeout alone;
- assert plan IDs, hashes, marker IDs, itinerary rows, diff, metrics, Evidence,
  and console/network status;
- exercise stale response ordering using delay-and-continue interception, never
  a fabricated response; and
- reload after confirmed acceptance; and
- in the separately invoked live test, type and submit through the actual
  website form, click the rendered `Add to draft` and `Preview repair` buttons,
  and prohibit direct adapter calls or fabricated product responses.

### One-command gates

The implemented deterministic, zero-provider command remains:

```powershell
python scripts/run_e2e1_vertical_slice.py \
  --output-dir results/e2e/<new_deterministic_run>
```

The authorized billed website-chat target command is separate and must be
impossible to invoke accidentally:

```powershell
python scripts/run_e2e1_vertical_slice.py \
  --live-copilot-chat \
  --confirm-billed-synthetic-context \
  --output-dir results/e2e/<new_live_chat_run>
```

The live command must reject a reused/nonempty output directory, occupied port,
missing OpenAI configuration, model/effort drift, prompt drift, more than two
transport attempts, non-synthetic context, or absent authorization flag before
or immediately after the boundary where that condition becomes knowable. It
starts/stops its own disposable app, runs only the one approved chat journey,
writes exact evidence, invokes structural readback, and exits nonzero on any
missing link. The deterministic command must still make zero provider calls.

## Explicit Non-Acceptance Conditions

E2E-1 does not pass merely because unit tests, schemas, JavaScript syntax, Ruff,
an HTTP 200, a backend child, a mounted map, mocked fetch tests, or screenshots
pass. It also fails if any panel remains on the parent while another presents
the child, geography is missing, an ineligible child is active, success appears
before map acknowledgement, only the original reported case is patched, or the
completion evidence omits exact inputs/outputs and identities. For E2E-1L it
also fails if the test calls GPT only from Python, bypasses the website chatbox,
uses a mocked Copilot response, stages without a visible proposal action,
previews a draft that does not match the provider intent, exceeds the authorized
attempt cap, omits exact provider bodies/usage/cost, leaks credentials, or leaves
the website map on a different plan than the evaluated child.

The valid completion statement is evidence-specific:

> The production-like browser journey generated child plan `<id>` from parent
> `<id>`, independently evaluated it as eligible under certificate `<id>`,
> rendered that same child in the itinerary and map with geometry hash `<hash>`,
> verified the expected Bixby/Pfeiffer marker change, and preserved identical
> plan identities across diff, metrics, Compare, Evidence, and acceptance.
